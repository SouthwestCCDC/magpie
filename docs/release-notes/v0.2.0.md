## Highlights

v0.2.0 is magpie's distribution release. The two-container setup (a Caddy
sidecar in front of the FastAPI app) is replaced by one **bundled container**
(Caddy and uvicorn under a single non-root supervisor). magpie now ships the
way a containerized service is expected to:

- A versioned image under the normal tags (`magpie:0.2.0`, `:0.2`, `:0`,
  `:latest`).
- A per-release `docker-compose.yml` and env template (`env.example`), both pinned to that
  image by digest, attached to the GitHub release.
- An image that is responsible for its own upgrade safety: it migrates the
  data format at startup and refuses data newer than it understands.

`magpie-deploy.sh` is still supported, and it is still the easiest way to
upgrade from v0.1.x: it takes a backup, swaps in the new version, checks the
result and rolls back automatically on failure. It is no longer required.
Plain compose and configuration-management tools such as Ansible are
first-class deployment paths.

The one case that needs action from you before upgrading is an install that
used magpie's **built-in TLS** (`TLS_MODE=auto|manual`). See below.

## Image tags

- `ghcr.io/southwestccdc/magpie:0.2.0`, `:0.2`, `:0` and `:latest` are the
  bundled image.
- `:0.2.0-bundled` (and `:<version>-bundled` for later releases) is kept as an
  alias, so pins taken from the release candidates keep working.
- The two-container backend image is no longer published. The existing v0.1.x
  images stay where they are.
- `:latest` and the major/minor tags only ever move to the newest stable
  release. A patch released on an older line can't pull them back.

## Deploying from release assets

Every release from v0.2.0 on attaches the files below. RC1-RC3 predate them, and
v0.2.0-rc4 has them, except that its env template is named `default.env.example`.
v0.2.0-rc6's `magpie-deploy.sh` fails on any command run without `--install-dir`,
so use rc7 or later:

| File | Contents |
|------|----------|
| `docker-compose.yml` | The image default is pinned by digest |
| `env.example` | The `.env.example` template, naming the same pinned image |
| `magpie-deploy.sh` | The installer for this release |
| `SHA256SUMS` | Checksums for the three files above |

To run a release with plain compose, download those files, verify them, set
up `.env` and run `docker compose up -d`. `MAGPIE_ADMIN_TOKEN_SINK` is
required: the container won't start until you choose how the first-boot admin
token is delivered. See `docs/releases.md` for the exact commands.

## HTTP-only, behind your proxy

- The container serves **plain HTTP on :8080 only**. TLS is terminated by
  your own reverse proxy in front of it.
- If you use `MAGPIE_ALLOWED_CIDRS`, or you care about client IPs, set
  `MAGPIE_TRUSTED_PROXIES` to your proxy's exact address. If
  `MAGPIE_ALLOWED_CIDRS` is set and `MAGPIE_TRUSTED_PROXIES` has never been
  set, `magpie-deploy.sh update` fails rather than continue.

## Runs as a non-root uid

New deployments no longer run as root. Before, every process in the
container ran as the owner of `/data`, and that owner is root for a
directory Docker or the installer created.

- **Plain compose:** `env.example` sets `MAGPIE_UID`/`MAGPIE_GID` to
  `10001`. Compose passes both through to the container. Leave them empty to
  keep the old behavior (run as the owner of `/data`).
- **Installer:** a fresh install creates a `magpie` system account, or
  reuses an existing one, and runs as it. If the data directory is already
  owned by a non-root uid, magpie runs as that uid instead.
- **Existing data keeps its owner.** `update` never changes the uid. On
  root-owned data it warns and points to the documented migration (stop,
  `chown -R`, set `MAGPIE_UID`/`MAGPIE_GID`, start). The image only chowns
  the data directory itself, not its contents. Setting a non-root uid on
  root-owned data without that `chown -R` makes the container exit with a
  permission error. See "Runtime user" in `docs/installation.md`.

## Starting without root (e.g. Kubernetes)

The image also starts when it's launched directly as a non-root uid
(`docker run --user`, or `runAsNonRoot` on Kubernetes), with every
capability dropped and a read-only root filesystem. In that case:

- The data directory must already be writable by that uid (on Kubernetes,
  `fsGroup`), since nothing in the container can chown it.
- With a read-only root filesystem, mount a writable `/tmp`. Caddy keeps
  its auto-saved config in a private directory there.
- Run one replica only: SQLite and the artifacts share one volume.

Containers started as root, which includes the compose file and the
installer, behave as before. See "Starting without root" in
`docs/installation.md`.

## Data-format migrations

- **The container migrates on start.** Before it serves traffic, it brings
  `magpie.db` to the data format its build supports. This happens under the
  init lock and in a single transaction. So "change the image tag and restart"
  is migrated just like an installer `update`.
- **A copy of the database is saved first.** Before a migration or a
  `migrate --to N` revert changes `magpie.db`, the image saves a copy with
  SQLite's online backup to `<data>/backups/magpie.db.<UTC timestamp>.pre-v<N>`
  (or `.pre-revert-to-v<N>`). The directory is `0700` and each copy is
  `0600`, since the copies hold token hashes. The newest 3 are kept. If the
  copy can't be written, nothing is migrated and the container doesn't start.
  The copies sit on the same volume, so they cover a bad migration, not disk
  loss. Restore steps are in `docs/backup-restore.md`.
- **Newer data is refused.** An image that finds data in a format newer than
  it supports exits without serving and without touching the database.
- **Downgrades are explicit.** `magpie-ctl migrate --to N`, run with the
  *newer* image, reverts its own migration steps down to version N. Then you
  can start the older image. Container startup never downgrades on its own.
  The procedure is under "Downgrading the data format" in
  `docs/installation.md`.
- v0.2.0's only migration stamps the data-format version (`PRAGMA
  user_version` 0 -> 1). It doesn't transform any data, and v0.1.x ignores
  the stamp, so going back to v0.1.x needs no revert step.

## Installer changes

- **`update` installs releases, not branch HEAD.** Plain `update` moves to the
  latest published stable release. `update --release <tag>` moves to exactly
  that tag (RCs included). `update --branch <name>` is for development only.
  If the release lookup fails, `update` stops instead of guessing. The
  installed release is recorded in `<install>/etc/.env` and shown by
  `magpie-deploy.sh status`.
- **Your compose override is honored.** If `<install>/docker-compose.override.yml`
  exists, the installer and its systemd units apply it on top of
  `docker-compose.yml`. Put site settings such as uid/gid, capabilities and
  extra environment there. `<install>/bin/magpie-compose` runs compose with
  the same set of files.
- The garbage-collection timer now runs cleanup in the bundled container. It
  no longer starts a second copy of the service.
- **Fixed: `uninstall` without `--purge` deleted the data** on installs that
  use the default data directory (`<install>/data`). This affects every
  v0.1.x installer and v0.2.0-rc1 to rc5. A plain `uninstall` now keeps the
  data directory, and `install` onto it reinstalls without `--force`.
  `uninstall --purge` removes the `magpie` account only if the installer
  created it.

## Built-in TLS is deprecated

- These installer flags now print a warning and do nothing. They will be
  **removed in v0.3.0**: `--tls-mode auto|manual`, `--domain`, `--tls-cert`,
  `--tls-key`, `--acme-server`, `--https-port`.
- If an existing install has `TLS_MODE=auto|manual`, **`update` fails**. Put
  an external TLS proxy in front of magpie first. Then re-run with
  `--accept-builtin-tls-removed` to acknowledge the change and continue.

## Upgrading from v0.1.x

**With the installer** (recommended for this upgrade):

1. If the built-in TLS section above applies to you, put your own proxy in
   front of magpie before upgrading.
2. If magpie sits behind a proxy, set `MAGPIE_TRUSTED_PROXIES`, or pass
   `--trusted-proxies`.
3. Download `magpie-deploy.sh` from this release, then run
   `sudo bash magpie-deploy.sh update --release v0.2.0`. A v0.1.x installer
   can't make the switch to the single container. `update` backs up the data,
   swaps the topology, checks data continuity and health, and rolls back
   automatically on failure.

**With plain compose:**

1. Back up the data directory.
2. Replace your compose file with this release's `docker-compose.yml`.
3. Add `MAGPIE_ADMIN_TOKEN_SINK` (and `MAGPIE_TRUSTED_PROXIES`, if you're
   behind a proxy) to `.env`. Don't copy `env.example`'s
   `MAGPIE_UID=10001` onto root-owned data unless you first `chown -R` it
   (see "Runs as a non-root uid").
4. Run `docker compose -f docker-compose.yml up -d`. The data directory is
   reused as-is, and the container migrates it at startup.

This was verified end-to-end on a real v0.1.6 install: `update` to the bundled
image kept the data byte-identical, and an injected failure rolled back
automatically.

## Not in this release

- Image signing and build provenance (#638).
- A Kubernetes example manifest, its CI, and a Helm chart.
- `magpie-ctl backup`, an on-demand online database backup (#660).
- The installer still clones the repository. Switching it to use the release
  assets is a later change; its command line won't change.
